# RPO：找到適合的產品技能

根據使用者要解決的問題與期望產出選技能，不要求使用者記住技能名稱。先判斷是否真的有相符技能；不要為了選出一個而硬套。

## 專案背景

開始前讀取目前工作專案根目錄的 `RPO-CONTEXT.md`；若檔案不存在或無法讀取，依對話中的資訊判斷。背景只用於理解任務，不把未確認內容當成事實；使用者當次指示優先。

## 選擇方式

1. 從使用者的描述辨識目前階段、要處理的對象，以及希望得到的產出。使用者明確指定其他技能時，依其選擇，不由 `rpo` 改派。
2. 對照下表選出最貼近**目前任務**的一個技能。若兩個技能的分界會改變處理方式，先問一個能分清用途的問題；不要要求使用者自行挑技能。
3. 只想知道「該用哪個」時，回答技能名稱、選擇理由及必要的使用範例。若使用者同時要求解決問題，說明選擇後直接讀取該技能的完整 `SKILL.md` 並依其流程接續工作，不讓使用者重複描述或再次輸入技能名稱。
4. 執行前確認所選技能在目前環境可用。若尚未安裝，只說明應安裝的 `skills/<名稱>/` 目錄與原因；不要聲稱已執行。若任務不屬於這套技能，明說沒有相符技能，依使用者原本的請求用一般方式協助。

| 目前要做的事 | 選用技能 |
|---|---|
| 還說不清真正的問題，想先釐清現象、原因假設與下一步 | `explore-problems` |
| 為產品定位或精實畫布整理「問題」與「現有替代方案」 | `initial-problem-discovery` |
| 辨識並比較潛在客群 | `market-segments` |
| 撰寫產品對目標顧客的價值主張 | `value-proposition` |
| 制定或檢視可衡量的產品目標 | `product-goals` |
| 驗證新產品需求，設計低成本實驗與成功門檻 | `brainstorm-experiments-new` |
| 將第一版產品縮小到最簡交付方式、定價與回饋機制 | `mvp` |
| 釐清一項模糊需求，評估是否值得做及可行方向 | `requirement-refinement` |
| 把需求寫成 User Story、Job Story 或 System Story 與驗收標準 | `pbi-template` |
| 將功能或 Epic 拆成可逐步交付的 backlog 項目 | `split` |
| 只要撰寫或檢視 Given–When–Then 驗收情境 | `ac` |
| 依產品價值與目標排序多項需求或 backlog | `priority` |
| 將對話中已有的價值主張、產品目標及市場客群同步到 `RPO-CONTEXT.md` | `stp` |
| 將目前對話整理給另一個 agent 接續 | `handoff`（需使用者明確呼叫） |

## 容易混淆的情況

- **探索問題／初始產品問題探索／需求釐清**：一般模糊想法用 `explore-problems`；目標是產品定位或精實畫布欄位用 `initial-problem-discovery`；已有具體需求要評估範圍與方向用 `requirement-refinement`。
- **實驗／MVP**：尚未知道市場是否有需求、要設計驗證方式用 `brainstorm-experiments-new`；已準備交付第一版、要縮小建置範圍用 `mvp`。
- **故事／拆解／驗收標準**：要寫單項 PBI 用 `pbi-template`；要把大項目分成多個可交付項目用 `split`；已有故事，只需補或檢查驗收情境用 `ac`。
- **產品目標／排序**：要定義成果與衡量方式用 `product-goals`；已有多個待辦項目要排先後用 `priority`。

一個請求若涵蓋多個階段，先處理完成當前目標所需的起點；只有後續步驟也在使用者原本的要求內，才繼續接力。所選技能的提問、確認、寫入及授權規則仍須遵守，`rpo` 不替它們跳過。`handoff` 設為明確呼叫，不能由 `rpo` 自動啟動；可告知使用者使用 `$handoff`。

## 設計參考

參考 [laoyeye 的技能路由方式](https://github.com/LearnPrompt/laoyeye/blob/main/skills/laoyeye/SKILL.md)：先確認有無相符技能，選出最合適的一個，並在可用時接續執行。本技能的對照與分界依本專案的技能調整。
